# DCR-002: 충돌 목록에서 마커 분류를 분리해 G4 예산을 회복한다

- 상태: 반영 완료 (승인 2026-07-31 사용자, 구현·검증 2026-07-31 — [record.md](record.md))
- 발견 위치: backlog.md §3.2·§3.3 (감사 확정 🔴, "막힌 지점" 상태)
- 현재 설계 기준선: design.md v2.2 (§4.10.7), ADR-47
- 관련 요구사항: G4(UI 단일 블로킹 ≤ 50ms), §1.3 모노레포 사용자
- 관련 ADR: ADR-47(대체 대상), ADR-75(상태 조회 실패를 조용히 넘기지 않는다)

## 변경 사유와 증거

ADR-47은 "워킹 트리를 읽지 않고 blob에게 물으면 예산 안"이라 했지만,
감사가 확인했듯 `_has_conflict_markers`의 `repo.get(id)`는 blob 내용을
ODB에서 로드한다 — 읽는 자리를 옮겼을 뿐 크기 의존성은 그대로다.
이 경로는 저장소를 열 때마다, 쓰기 큐가 빌 때마다 UI 스레드에서 돈다.

**2026-07-31 실측(macOS, Apple Git-155, 이 저장소의 엔진 코드로 측정):**

| 입력 | 현행 전체 스캔 | 경로·종류만 열거 |
|------|---------------|-----------------|
| 충돌 200개 × 100줄 | 26ms | 1.2ms |
| 충돌 1,000개 × 100줄 | 144ms (G4의 2.9배) | **5.9ms** |
| 충돌 200개 × 20,000줄 | 2,957ms (G4의 59배) | **1.4ms** |

비용의 원천은 목록이 아니라 **마커 분류(blob 로드)뿐**이다. 분류를 빼면
열거는 파일 크기와 무관하게 G4 예산의 12% 이내다.

재현 스크립트: `experiments/exp_scan.py` (이 디렉터리에 보존).

backlog §3.2의 "막힌 지점"은 *스캔 전체를 워커로 옮기면* 충돌 목록을
동기적으로 읽는 소비자(배너·메뉴 잠금·원격 액션)에 "아직 모름" 상태가
생긴다는 것이었다. 그러나 **동기 소비자들이 실제로 쓰는 것을 확인한 결과
전부 경로·개수뿐이고, `has_markers`를 읽는 곳은 충돌 패널의 행 표시와
병합 직후 안내문뿐이다** (main_window.py:1220·2003). 즉 비대화면
경로에서 blob을 로드할 이유가 애초에 없다 — "아직 모름" 상태를 새로
설계할 필요 없이, 비싼 절반을 분리하면 된다.

## 기존 설계

- `index_conflicts()` / `merge_conflicts()`가 열거와 마커 분류를 한 번에
  수행하고, `ConflictedFile.has_markers`가 즉시 채워진다 (ADR-47).
- `conflict_detail()`도 UI 스레드에서 blob 전체를 읽는다 (backlog §3.3 —
  같은 원인의 이웃 결함).

## 제안 설계

**충돌 목록(싸다, 동기 유지)과 마커 분류(비싸다, 지연)를 분리한다.**

1. `index_conflicts()`는 경로와 충돌 종류(side)만 채운다 — 인덱스만 읽고
   blob은 열지 않는다. 동기 소비자(배너 개수, 메뉴 잠금, 원격 액션 가드,
   `continue_operation`의 잔여 충돌 검사)는 그대로 동작한다. 삭제 계열의
   `has_markers=False`는 side만으로 판정되므로 지금처럼 즉시 안다.
2. `has_markers`(텍스트 병합 여부)는 **워커에서 지연 분류**한다.
   기존 로더 패턴(RefsLoader·DiffLoader — Phase 1 G4 초과를 같은 방식으로
   해소한 전례)을 재사용해 `ConflictLoader`를 둔다. 충돌 패널은 행을 먼저
   그리고, 분류가 도착하면 "한쪽 선택만 가능" 표시를 갱신한다.
   분류 전 행은 중립 표시(두 경로 모두 노출) — ADR-75가 막은 "아무 일
   없음 날조"가 아니라, 아직 좁히지 않은 것이다.
3. 병합 직후 안내문의 markerless 목록(main_window.py:1220)은 병합 자체가
   워커에서 끝난 뒤의 결과이므로, 같은 워커 문맥에서 분류를 마치고
   `MergeOutcome`에 실어 온다 — UI 스레드 비용 0.
4. **인접 정리(같은 원인, backlog §3.3):** `conflict_detail()`과
   `_working_copy_edited`의 blob 읽기도 `ConflictLoader`로 옮긴다.
   해결 버튼은 상세가 준비된 뒤 활성화된다.

### 기각한 대안

- **전체 스캔 워커화 + 3-상태(UNKNOWN) 도입**: 동기 소비자 전부에
  "아직 모름" 분기가 생기고, 그 상태에서 메뉴·원격 가드가 무엇을 할지
  전부 새로 정해야 한다. 실측상 동기 경로가 이미 예산 안이므로
  치러야 할 복잡도에 대응하는 이득이 없다. (다만 인덱스 자체가 수십만
  항목인 극단 저장소에서 열거가 예산을 넘으면 그때 이 대안으로 확장한다 —
  분리해 둔 구조는 그 확장을 막지 않는다.)
- **blob 크기 상한 휴리스틱**(큰 blob은 텍스트로 가정): ADR-47과 같은
  종류의 "옮겼을 뿐인" 해법이고, 잘못 분류하면 바이너리 충돌에 편집기
  경로를 안내한다.

## 변경 항목

| 위치 | 기존 | 변경 | 이유 |
|------|------|------|------|
| `ConflictedFile.has_markers` | `bool`, 즉시 채움 | `bool \| None` (None = 미분류) 또는 열거/분류 타입 분리 | 목록에서 blob 로드 제거 |
| `_collect_conflicts()` | 파일마다 `_has_conflict_markers()` 호출 | side 기반 즉답만 (삭제 계열 False), 텍스트 여부는 미분류로 | 크기 의존성 제거 |
| application 층 | — | `ConflictLoader` (RefsLoader 패턴) — 마커 분류·상세 로드 | §3.3 규칙: 읽기는 워커 |
| `conflict_panel` | has_markers 즉시 표시 | 분류 도착 시 갱신, 상세 준비 후 해결 버튼 활성화 | ADR-75 준수 |
| `MergeOutcome` 경로 | UI 스레드에서 분류 | 병합 워커에서 분류 완료 후 전달 | UI 비용 0 |

## 영향 범위

- 공개 인터페이스: `ConflictedFile` 도메인 모델 변경 — 소비자는 앱 내부뿐
- ADR-47: 새 ADR로 **대체** (판정 위치를 blob으로 옮긴 것이 아니라, 판정
  시점을 임계 경로 밖으로 옮긴다). ADR-47 본문은 절차대로 수정하지 않는다.
- ADR-63·64·75와 충돌 없음 — 충돌을 감추는 방향이 아니라 분류만 늦춘다.
- 성능: 저장소 열기·쓰기 큐 idle 경로에서 최악 2,957ms → ~6ms

## 구현된 코드의 처리

`_has_conflict_markers`의 판정 로직 자체(바이너리 여부 기준)는 옳으므로
`ConflictLoader`로 이동해 재사용한다. 삭제·유지·이동을 명확히 구분한
목록은 구현 계획(Workflow 2)에서 작성한다.

## 마이그레이션 및 롤백

데이터 마이그레이션 없음. UI 상태 추가(미분류 표시)는 롤백 시 코드
되돌리기로 충분하다.

## 검증 방법

- 실측 하네스(experiments/exp_scan.py)를 회귀 테스트로 승격: 충돌 1,000개
  ×100줄에서 `index_conflicts()` ≤ 50ms (AC: G4)
- 충돌 200개 × 20,000줄(대형 파일)에서도 동일 (AC: 크기 무의존)
- 분류 도착 전 행 표시가 두 경로를 모두 노출하는지 (ADR-75)
- markerless 안내문이 병합 직후 정확한지 (기존 test_merge_ui 확장)
- stash pop 충돌(상태 NONE)에서도 목록·분류가 동작 (ADR-63 회귀)
